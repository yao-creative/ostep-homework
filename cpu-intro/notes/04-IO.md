Right — my notation

$$
IO \rightarrow IO,\ IODONE
$$

was **not meant to imply that the code has a function literally written `IO -> IO, IODONE`**. It was my algebraic description of what the parser does.

In the code, it is implemented explicitly as **two `append()` operations**.

The relevant part is:

```python
elif opcode == DO_IO:
    proc['code'].append(DO_IO)
    proc['code'].append(DO_IO_DONE)
```



### 1. What the code starts with

The constants define:

```python
DO_COMPUTE = 'cpu'
DO_IO = 'io'
DO_IO_DONE = 'io_done'
```

So:

$$
IO = \texttt{'io'}
$$

and

$$
IODONE = \texttt{'io\_done'}
$$



---

### 2. The input `i`

Suppose the explicit program is:

```text
c3,i,c2
```

The parser sees:

```python
opcode = op[0]
```

so for `i`:

$$
opcode = \texttt{'i'}
$$

Then it executes:

```python
proc['code'].append(DO_IO)
proc['code'].append(DO_IO_DONE)
```

Therefore:

$$
\boxed{
\texttt{i}
\mapsto
[\texttt{'io'},\texttt{'io\_done'}]
}
$$

That is what I was abbreviating as:

$$
\boxed{
IO \mapsto IO\cdot IODONE
}
$$

where `·` means **sequence/concatenation**, not function composition.

---

### 3. Why does it need two instructions?

Because the simulator models an I/O operation as two conceptual events:

$$
\boxed{
IO \rightarrow IODONE
}
$$

The first:

$$
IO
$$

means:

> The process requests/starts I/O and becomes waiting.

Later, when the simulated I/O finishes:

$$
IODONE
$$

is used as the corresponding completion action.

You can see the runtime handling the actual `DO_IO` action here:

```python
if instruction == DO_IO:
    self.move_to_wait(current)
    io_finish_times[current] = clock_tick + self.io_length + 1
```



So there are really **two levels**:

$$
\boxed{
\text{input token } i
\quad\mapsto\quad
[\text{IO},\text{IODONE}]
}
$$

and then the runtime interprets those semantic instructions.

---

### 4. Important correction to my earlier notation

I would now write it more precisely as:

$$
\boxed{
parse(\texttt{i}) = [IO, IODONE]
}
$$

rather than

$$
IO \rightarrow IO, IODONE
$$

because the latter can look like a state transition or function.

The algebra is:

$$
\boxed{
i \mapsto IO\cdot IODONE
}
$$

where:

* \(i\) = **concrete syntax token**
* \(IO\) = **semantic instruction**
* \(IODONE\) = **semantic instruction**
* \(\cdot\) = **sequence concatenation**

So for the whole explicit program:

$$
\texttt{c3,i,c2}
$$

you get:

$$
\boxed{
[CPU,CPU,CPU]\cdot[IO,IODONE]\cdot[CPU,CPU]
}
$$

which simplifies to:

$$
\boxed{
[CPU,CPU,CPU,IO,IODONE,CPU,CPU]
}
$$

That distinction between **syntax (`i`) → semantic instruction sequence (`IO · IODONE`)** is the key thing to keep separate.
