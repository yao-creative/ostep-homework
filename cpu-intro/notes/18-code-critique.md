## Funnel: fidelity → cleanliness → per-unit formalization

Before rating anything, the causal precedent is: **does it execute and match doc2's observable behavior (fidelity)?** Only once that's settled does **cleanliness of the abstraction boundaries** become the meaningful axis to critique. I checked both by tracing execution, not just reading structure.

### Fidelity: currently 0% — new Level-0-class bugs were introduced while others carried over

This version reorganizes correctly in *shape* but the wiring between the new pieces has fresh breakage of the same category as before (arity/attribute/return-type mismatches). In call order:

1. **`new_process`** — unfixed from before: `scheduler_state.proc_info[proc_id] = {}` then `.pc = 0` — attribute-assignment on a dict. Crashes on the very first process load, before anything else runs.
2. **Config field-name drift, three separate spots** — `SchedulerConfig`'s real fields are `process_switch_policy`, `io_done_policy`, but: `new_scheduler_config_from_options` constructs it with kwargs `process_switch_behavior=`/`io_done_behavior=` (→ `TypeError`, wrong keyword); `handle_io_done_process_switching` then reads `scheduler_config.io_done_behavior` / `.process_switch_behavior` (→ `AttributeError`, those attributes don't exist even on a correctly-built instance). Only `handle_io_issue`'s `scheduler_config.process_switch_policy` is spelled right. This is a **naming inconsistency across the seam you just introduced** — the config type and its consumers were edited independently.
3. Enum construction is also wrong even with correct kwargs: `SchedulerSwitchPolicy(options.process_switch_behavior)` looks up an enum **by value**, but `options.process_switch_behavior` is the string `'SWITCH_ON_IO'`, while the enum's actual values are `auto()`-assigned ints. You want `SchedulerSwitchPolicy[options.process_switch_behavior.removeprefix('SWITCH_')]` or a name-keyed lookup — value-lookup will raise `ValueError` regardless of the kwarg fix.
4. **`resolve_io_done`** has no `return` statement at all — falls off the end returning `None` unconditionally (whether or not the `if` fires). It's called as `scheduler_state = resolve_io_done(...)` inside a loop over every pid, so `scheduler_state` becomes `None` after `pid=0` regardless of branch outcome, and the next iteration crashes on `None.io_finish_times`. It also still calls `get_proc_info_by_pid(scheduler_state, pid)` with **arguments reversed** (signature is `(pid, scheduler_state)`) — a `KeyError`/`TypeError` even before the missing-return matters.
5. **`handle_io_issue`** — same missing-return shape: the early-exit branch returns correctly, but the "instruction was IO" branch computes `scheduler_state` and never returns it, falling off the end as `None`.
6. **`handle_scheduler_step`**'s final line is `return scheduler_state,` — the trailing comma makes this a **1-tuple**, not `(scheduler_state, scheduler_metrics)`. The caller in `run()` does `scheduler_state, scheduler_metrics = handle_scheduler_step(...)` — unpacking a 1-tuple into two names raises `ValueError: not enough values to unpack`.
7. **`emit_scheduler_state_per_tick`** does `'RUN:' + curr_instruction` where `curr_instruction` is an `Instruction` enum member, not a `str` — `TypeError`. Needs `curr_instruction.name`.
8. **`emit_instruction`** compares `curr_instruction == "COMPUTE"` — again enum-vs-string; this comparison is *never* true (the actual value is `Instruction.COMPUTE`), so the CPU column silently prints nothing even when compute executes — a silent-failure sibling of bug 7, same root cause (forgot `.name`/`.value` when the enum refactor happened).
9. **`next_proc`**'s wraparound branch still references the undefined bare name `proc_info[pid]` instead of `get_proc_info_by_pid(pid, scheduler_state)` — carried over unfixed.
10. **`resolve_instructions_done`** still computes `transition_to_done(curr_proc_info, ProcessState.RUNNING)` and discards it — the get→transform→forget-to-write-back pattern from before, still present, unfixed.
11. **No initial `next_proc(scheduler_state, pid=0)`** before the loop in `run()`. Doc2 explicitly does `self.move_to_running(STATE_READY)` for pid 0 before entering the loop. Without it, process 0 never leaves `READY`, `handle_execute_instructions`'s `state == RUNNING` guard never fires, nothing is ever popped, `get_num_active` never changes → **infinite loop**, not just a wrong trace.

None of these are subtle logic errors — they're all *signature/contract mismatches introduced or left at the seams between newly-split functions*. The underlying architectural idea (splitting `resolve_io_done` / `handle_io_issue` / `accumulate_metrics` / `emit_*` into single-purpose units) is sound; the composition wasn't type-checked against itself.

### Cleanliness: real improvement in decomposition, undermined by unverified composition

The naming discipline is now good — `resolve_*`, `handle_*`, `emit_*`, `accumulate_*` each signal a distinct Lampson role instead of one monolithic `run`. The comments formalizing transitions as tuples-in/tuples-out (e.g. the `(Immediate x (Pid != Curr_proc) x RUNNING x ...)` annotations) are a genuine improvement in self-documentation of the guard conditions. The failure mode is that **splitting a function into N functions multiplies the number of interface contracts that must agree**, and none of those contracts were exercised end-to-end before this was called a fix — the file cannot currently import-and-run past the first process load.

## Per-unit table

**Lampson-role taxonomy used below** (mechanism/policy separation, atomicity, simple interfaces): *Constructor* ($\varnothing\to X$), *Pure reader* (projection out of the state), *Guarded partial transition* (a morphism restricted to a precondition, per Hoare/Lampson "keep the normal case clean, handle the abnormal case separately"), *Lens/mutator* (get–set pair), *Policy dispatcher* (mechanism parameterized by `SchedulerConfig`), *Effect* (non-referentially-transparent I/O), *Orchestrator* (composition of the above), *Driver* (top-level entry point).

| Unit | Lampson role | Formal signature | Critique |
|---|---|---|---|

Pick index-into-tuple *or* drop the annotation. |

---

**Net assessment against Lampson's "make actions atomic" hint**: the recurring bug — forgetting to write a transformed value back into `SchedulerState` (`resolve_instructions_done`) or forgetting to `return` the accumulated state at all (`resolve_io_done`, `handle_io_issue`) — is the *same* atomicity violation showing up in three different functions across two review rounds. That's a signal to fix it once, structurally, via a single `update_proc_info(pid, f, state) -> state` combinator that every transition is forced through, rather than continuing to patch each occurrence individually as it's discovered.
